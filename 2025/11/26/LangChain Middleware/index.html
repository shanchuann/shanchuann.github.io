LangChain Middleware

发表于2025-11-26|更新于2026-10-05|LangChain
|浏览量:

代码仓库ChainReaction

中间件这个词已经被用滥了。Web 框架拿它做鉴权，Django 拿它记请求日志。放到 agent 上，意思没变：在不改核心循环的前提下，在固定位置插一段自己的代码。

create_agent 返回的是一张编译好的 LangGraph 图，循环逻辑写死在图里。你想加一句”每次调用模型前打印当前消息数”，有两个选择。自己用 StateGraph 重画一遍循环，或者把这段逻辑做成中间件塞进 middleware=[...]。前者的代价是官方每次调整循环你都得跟着改，后者只多一个参数。

这篇文章把 middleware 这个参数讲清楚。钩子挂在哪些位置，装饰器和类两种写法各适合什么场景，状态怎么在钩子之间传，内置中间件有哪些能直接拿来用，多个中间件叠在一起时谁先谁后。最后有两个完整例子：按对话长度动态换模型，以及工具抛异常之后怎么让 agent 活下来。

所有代码都在 DeepSeek 上跑过，输出是从终端直接复制的，脚本放在 Middleware/。

中间件挂在循环的哪一步

先看循环本身。模型读一遍消息，决定要不要调工具。要调就执行工具，把结果作为 ToolMessage 塞回消息列表，再问一次模型。直到某次回复里没有 tool_calls，循环结束。

中间件做的事，是在这个循环的每个转折点放一个钩子。

    flowchart TD
    A([agent.invoke]) --> B[before_agent 每次调用执行一次]
    B --> C[before_model 每个模型调用前]
    C --> D[wrap_model_call 进入]
    D --> E[模型生成回复]
    E --> F[wrap_model_call 返回]
    F --> G[after_model 每个模型回复后]
    G --> H{回复里有 tool_calls 吗}
    H -- 有 --> I[wrap_tool_call 进入]
    I --> J[执行工具]
    J --> K[wrap_tool_call 返回]
    K --> C
    H -- 没有 --> L[after_agent 每次调用执行一次]
    L --> M([返回最终状态])

六个钩子里，四个是节点式的，位置固定，按顺序执行。两个是包裹式的，包住一次模型调用或一次工具调用。

有件事容易忽略：中间件不是独立的运行时。钩子就跑在 create_agent 编译出来的那张图里。你可以把整个 agent 当成节点或子图塞进更大的 StateGraph，HITL 中断、摘要、PII 脱敏、重试这些行为会跟着 agent 一起走，不用重新配。

中间件能插手的地方，官方文档列了四类：追踪 agent 行为（日志、埋点、调试），改写提示词和工具选择，加重试、降级和提前终止，加限流、护栏和 PII 检测。前两类是看和改，后两类是控。

六个钩子，两种脾气

钩子 类型 触发时机
before_agent 节点式 agent 开始前，一次调用执行一次
before_model 节点式 每次模型调用前
after_model 节点式 每次模型回复后
after_agent 节点式 agent 结束后，一次调用执行一次
wrap_model_call 包裹式 包住每次模型调用
wrap_tool_call 包裹式 包住每次工具调用

节点式钩子的签名是 (state, runtime)，返回一个 dict 或 None。包裹式钩子的签名是 (request, handler)，拿到请求，自己决定 handler 什么时候调、调几次。

差别就落在”调几次”上。节点式钩子拦不住模型调用，想提前退出只能返回 jump_to，这一点后面单独说。wrap_model_call 可以一次都不调 handler，直接返回一个自己造的 ModelResponse；也可以循环调三次，这就是重试中间件的实现方式。

钩子签名里的 runtime 是本次调用的运行时对象，runtime.context 里放着通过 context_schema 声明的每轮数据，比如 user_id、feature flag。包裹式钩子从 request.runtime 拿到的是同一个对象。要做”按用户等级决定能不能调这个工具”这类逻辑，读它就够了。

状态更新的路径也不一样：

  • 节点式钩子返回 dict，dict 按图的 reducer 合并进 state
  • wrap_model_call 要注入状态，得返回 ExtendedModelResponse(model_response=..., command=Command(update={...}))
  • wrap_tool_call 直接返回 Command

多个中间件都返回 ExtendedModelResponse 时，command 会依次应用。非 reducer 字段是内层先写、外层后写，键冲突时外层赢。外层如果做了重试、handler 被调了多次，前面几次的 command 会被丢掉，不会污染最终状态。

装饰器式 类式
适合 单个钩子、逻辑十行以内、原型阶段 多个钩子、需要构造参数、同步异步都要
写法 @before_model 修饰函数 继承 AgentMiddleware，覆盖方法
声明状态 @before_model(state_schema=MyState) class MyMW(AgentMiddleware[MyState]): state_schema = MyState
声明可跳转 @before_model(can_jump_to=["end"]) 方法上加 @hook_config(can_jump_to=["end"])
附带工具 装饰器传 tools=[...] 类属性 tools = [...]

AgentMiddleware 子类还能声明三个类属性，工厂在编译期会读：state_schema 扩展状态字段，tools 注册随中间件一起提供的工具，transformers 注册流式转换器。TodoListMiddleware 给 agent 加的 write_todos 工具就是通过 tools 注册的。

选哪个没有硬规则。我的习惯是：一个钩子、逻辑短，用装饰器；出现第二个钩子，或者需要构造函数传阈值、传模型，就换类。需要在 invoke 和 ainvoke 两条路径上都跑，也只能用类，因为装饰器生成的中间件没有独立的异步实现。

名字 解决什么问题 关键参数

LLMToolSelectorMiddleware 工具太多时先让模型挑出相关的几个 model、max_tools、always_include

中间件顺序

多个中间件叠在一起时的规则，文档写得很清楚：

    flowchart TD
    subgraph BEFORE[before 钩子 按列表顺序]
      direction LR
      b1[M1.before_model] --> b2[M2.before_model] --> b3[M3.before_model]
    end
    subgraph WRAP[wrap 钩子 逐层嵌套]
      direction TB
      w1[M1 进入] --> w2[M2 进入] --> w3[M3 进入] --> mm[模型] --> w3r[M3 返回] --> w2r[M2 返回] --> w1r[M1 返回]
    end
    subgraph AFTER[after 钩子 反向]
      direction LR
      a3[M3.after_model] --> a2[M2.after_model] --> a1[M1.after_model]
    end
    BEFORE --> WRAP --> AFTER

三条规则：before 正序，after 倒序，wrap 嵌套（第一个中间件包住所有后面的）。

排序的经验，按重要性排：

  • 会短路、做校验的放前面。后面的钩子直接不跑，省掉无谓开销。
  • 日志类的放前面，能看到最原始的入参。放在后面看到的是被别的中间件改过的版本。
  • 重试类的放里面。官方文档里 ToolErrorMiddleware 和 ToolRetryMiddleware 的组合就是 error 在外、retry 在内，而且 retry 要配 on_failure="error"，让重试次数用尽后的异常冒到外层去兜。

短路

想提前结束，返回的 dict 里带 jump_to。三个目标：

  • 'end'：跳到 agent 结束，或者第一个 after_agent 钩子
  • 'tools'：跳到工具节点
  • 'model'：跳到模型节点，或者第一个 before_model 钩子

返回 jump_to 的钩子必须声明 can_jump_to。装饰器写法是在参数里写 @before_model(can_jump_to=["end"])，类写法是在方法上加 @hook_config(can_jump_to=["end"])。

'model' 这个目标用得少一些。一个场景是在 after_model 里发现回复格式不对，把最后一条替换成新的 AIMessage，再跳回模型节点让它重说一遍。

例子二：工具抛异常之后

同样的事，内置的 ToolErrorMiddleware 一行配置就够，不用自己写 handler：

on_error 的返回值控制信息披露。返回字符串，异常就变成 error ToolMessage；返回 None 或干脆不 return，异常继续上抛，run 会终止。文档建议返回异常类型而不是原始异常消息，因为原始消息里可能带着内部细节，比如数据库连接串。ToolErrorMiddleware 需要 langchain>=1.3.14，本地的 1.4.3 没问题。

    触发摘要 --> 累积消息: 摘要 + 最近 keep 条替换历史

小结

  • 中间件是挂在 agent 循环固定位置的钩子。节点式钩子管顺序和状态，包裹式钩子管 handler 被调几次。
  • 执行顺序是 before 正序、after 倒序、wrap 嵌套。同名中间件会触发 AssertionError，用子类或 name= 区分。
  • 自定义状态用 state_schema 加 NotRequired 字段，钩子返回的 dict 自动合并，计数、标记、审计信息都能挂在上面。
  • 内置中间件覆盖了重试、兜错、摘要、HITL、PII、限流、任务规划。动态提示用 @dynamic_prompt，动态模型用 @wrap_model_call 加 request.override(model=...)。
  • LLMToolSelectorMiddleware 四条通路都跑不通，但原因分两类。DeepSeek 报 400，Ollama 云端无论兼容端点还是原生端点都是解析器拿到非 JSON 后抛 OutputParserException，这是 provider 不支持结构化输出。Gemini 上 provider 支持了，中间件却因为选择 schema 把工具描述写进了 Literal 的 description，模型把描述当值返回，抛 ValueError: Model selected invalid tools。换 system_prompt 补不上，因为约束在 schema 里。工具筛选用 @wrap_model_call 加 request.override(tools=...) 自己写，实测可行。摘要、重试、动态模型、工具兜错都正常。
