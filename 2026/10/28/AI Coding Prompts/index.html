AI Coding Prompts

发表于2026-10-28|更新于2026-10-28|AI
|浏览量:

最近在投简历遇到了不少 AI Coding 笔试。

这类考试的形式大同小异：给你一个现成仓库和一份 README，要求在限定时间内实现需求，有的还会让你根据测试反馈反复修改。说起来就是”用 AI 写代码”，但真上手我才发现，把题目往对话框里一贴、让它自由发挥，基本等于开盲盒。我第一次做的时候，AI 吭哧吭哧写了一大堆，跑起来一看，需求漏了一半，还顺手把原本能跑的代码给重构了。

后来我慢慢固定下来一套流程：把一次考试拆成 6 个步骤，每一步都要求 AI 先输出具体结果，我确认之后再进入下一步。这套提示词我自己一直在用，贴在这里存档，也方便以后直接复制。

整体流程是这样的：

  1. 需求对齐：读 README、读代码，先和 AI 形成共同理解
  2. 架构设计：让它整理出一份可执行的开发 spec
  3. 拆分 + 开发：把 spec 拆成 tickets，一次只实现一个功能点
  4. Code Review：对照 ticket 和 spec 检查实现质量
  5. 验收测试：对照 README 逐条核对完成度
  6. 定点修复：根据测试反馈找根因，小范围修改

核心就一句话：别让 AI 一路自由发挥。

第 1 步：需求对齐

刚拿到题目的时候，我以前总急着让它写代码，结果写出来的东西经常和题目对不上。现在我会先把这一步走完，全程不写一行代码。

做法是让 AI 先把 README、目录结构、已有测试和核心代码都读一遍，然后反过来追问我。它问的问题按一棵”决策树”来组织，每轮只问当前前置条件已经明确的问题；能自己读代码查到的事实，不许拿来问我。

这一步看起来慢，但我觉得是最值的。很多题目的坑就藏在 README 的一句话和已有代码的约定里，等它写完再发现，返工的成本高得多。

第 2 步：架构设计

需求对齐之后，我会让它输出一份开发 spec，把”这个项目怎么跑、准备怎么改”讲清楚，包括已知信息、功能点拆解、实现思路、测试方式、不做什么和风险点。

我自己最看重”不做什么”和”风险点”这两节。AI 实现需求时很容易顺手加戏，提前把边界写死，后面能少很多麻烦。

第 3 步：拆分 + 开发

有了 spec，我不会让它一口气全做，而是先拆成一组小 ticket，每个 ticket 小到一个会话能完成，有明确的边界、验收标准和测试，再按依赖顺序排好。

然后一个 ticket 一个 ticket 地实现，每次只做当前这一个：

一次只喂一个 ticket，是我踩过坑之后学到的。让它一次做五件事，它大概率会漏掉两件，还把不相关的代码搅在一起，到时候都不知道该从哪查起。

第 4 步：Code Review

每做完一个 ticket，我会立刻让它 review 自己的改动，而不是攒到最后一起看。

这一步经常能抓到它自己几分钟前刚写出来的边界 bug，成本就是多等一轮对话，很划算。

第 5 步：验收测试

Review 通过之后，再做一次整体验收，对照 README、ticket 和 spec 逐条列表：需求、验收标准、实现位置、测试证据、当前状态。这一步只验收，不改代码。

记住测试通过不等于需求完成，必须逐条对照题目要求。发现问题先记录现象、证据、影响范围和建议修复位置，等我确认之后再动手。

第 6 步：定点修复

最后是修 bug。测试通过率上不去的时候，我不让它直接动手改，而是先输出一张”失败卡片”，列出最多 3 个根因假设，每个假设写清支持证据和验证方式，然后只挑最可能、影响面最小的一个来修。

修之前先写一个能复现问题的测试或验证步骤，改完让它给我复测命令；在我贴回运行结果之前，它只能说”待验证”，不能说”已修复”。

这套流程能保住的是下限。只要每一步都认真确认，AI 基本不会写嗨了做偏题，也不会把原本能跑的代码改崩，基本完成度是有的。

但它也就到此为止了。想冲高分、想过那些隐藏测试，模板帮不上忙，还是得自己读得懂代码结构、理得清业务规则、想得到边界情况。提示词管的是流程，最后拼的还是自己的判断力，这点我也还在练。
